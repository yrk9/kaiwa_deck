# 技術選定

## 結論
フロントエンドはNext.js(React)、バックエンドはFastAPIを採用する。

## フロントエンド: Next.js(React)の選定理由

**対抗馬**: Vue.js/Nuxt.js、Svelte/SvelteKit、SolidJS、Remix、Angular、Astro

**重視した軸**: アプリとの相性、就活でのアピール(開発者はReact/Next.js以外のフロントエンド技術は未経験)

- **アプリとの相性**: カードめくり演出(Framer MotionはReactエコシステムの中核ライブラリで、状態管理と宣言的に連携できる。対抗のSvelteも標準transition機能が強力だが周辺ライブラリの厚みはReactに劣る)、リアルタイムWebSocket(`useEffect`ベースのカスタムフックで接続ライフサイクルを複数画面から再利用しやすい)、shadcn/ui・TanStack Query等の採用予定ライブラリがReactエコシステムに集中しており統合の摩擦が少ない、Next.js App RouterによるServer/Client Componentsの使い分け(LPは軽量に、ドロー画面はインタラクティブに)
- **就活でのアピール**: フロントエンド求人で最も要求頻度が高い技術の一つで訴求力が高い。Next.jsのApp Router/Server Actionsといったモダンな実践経験も評価されやすい。対抗馬のVue/Svelteも技術的に劣らないが、新卒・インターン採用市場ではReact系の需要が圧倒的に高い
- **結論**: 経験の有無を抜きにしても、アプリとの相性・アピール力の両軸で他候補に劣る点が見当たらず、React/Next.jsを積極的に選ぶ合理性がある

### 補足: React単体(Vite等)ではなくNext.jsを使う理由
バックエンドはFastAPIに完全分離するため、Next.jsの「フルスタック機能」(Server Actions、DB直接アクセス等)はほぼ使わず、実質的には「ルーティングとビルドが標準装備されたReact」として使うことになる。それでも素のReact+Vite+React Routerではなく**Next.jsを採用する**のは以下の理由による。
- 複数画面(`/`, `/play`, `/room/[code]`, `/decks`, `/decks/[id]`, `/history`, `/account`等)のファイルベースルーティングが標準搭載されており、React単体でReact Routerを別途セットアップする手間が省ける
- Vercelへのデプロイが最もスムーズ(Next.js自体がVercelの製品)
- LPページ(`/`)で多少SEOを意識する場合、SSRが有利(React単体のSPAはクローラーに弱い)
- 日本のフロントエンド採用市場ではNext.js経験の方が言及頻度・知名度が高く、就活アピールの面でReact単体構成より訴求力が出やすい

## バックエンド: FastAPIの選定理由

1. **実装コストの低さ**: これまでの学習履歴でFastAPIの使用経験があり、学習コストをかけずに実装速度を確保できる。浮いた時間をUI/UX(カード演出等)の作り込みに割ける
2. **並列処理が不要な可能性が高い**: このアプリのワークロード(デッキ/カードCRUD、ソロドロー、ルーム内のWebSocketブロードキャスト、Phase2のLLM API呼び出し)はすべてI/Oバウンドが支配的で、CPUバウンドな重い計算処理は発生しない。Goのgoroutineが持つ「マルチコアでの真の並列実行」という強みが活きる場面がほぼなく、PythonのasyncioによるI/Oバウンドな並行処理で要件を満たせる
3. **CRUD/API設計を学びたいという動機に合致**: FastAPIはPydanticによる型安全なスキーマ定義、自動OpenAPI(Swagger)生成、RESTfulなエンドポイント設計を体系的に学べるフレームワークであり、Supabase完結案(BaaSがCRUD層を肩代わりしAPI設計を学ぶ機会が少ない)よりも学習目的に合致する

### 比較検討の経緯(要約)
- **Supabase Realtime完結案**: 実装量・コストは最小だが、テーブルを直接叩く設計のためRESTfulなAPI設計そのものを学ぶ機会が少なく、今回の学習動機と合わない
- **Go**: 実行速度・並行処理性能は最も高いが未経験で学習コストが高く、かつ本アプリでは並列処理の恩恵をほぼ活かせない
- **PartyKit(Cloudflare)**: リアルタイム共有のユースケースには強いが、認証・DB機能がなく外部サービスとの組み合わせが前提。エコシステムもニッチで情報が少ない
- **結論**: 「学習コストの低さ」「API/DB設計の学習効果」「本アプリのワークロードとの適合性」のバランスでFastAPIが最良

## 認証方針
FastAPI側で認証をフルスクラッチ実装するのはセキュリティリスクと工数の両面で非合理なため、**Supabase Auth**(匿名認証+メール等でのアカウント昇格)を採用し、FastAPI側はSupabase発行のJWTを検証するミドルウェアのみ実装する。これによりゲスト利用(ログイン不要)とアカウント機能(デッキ永続保存)を両立しつつ、認証部分の実装コストを最小化する。

## DB
Supabase Postgres。Auth(上記)との統合が容易で、勝率集計等のGROUP BYクエリも標準SQLで書きやすい。FastAPIからはSQLAlchemy等のORM経由、またはSupabaseのPostgres接続情報を直接使う形でアクセスする。

## リアルタイム共有の実現方法
FastAPIのWebSocketエンドポイント(`@app.websocket`)+ `asyncio.Lock`による部屋単位の排他制御で自前実装する。Goで書く場合とほぼ同じ構造だが、Pythonの非同期構文で完結する。

```python
class Room:
    def __init__(self):
        self.connections: list[WebSocket] = []
        self.drawn_card_ids: set[str] = set()
        self.lock = asyncio.Lock()

    async def draw(self, deck_id: str) -> Card:
        async with self.lock:
            available = [c for c in self.deck if c.id not in self.drawn_card_ids]
            card = random.choice(available)
            self.drawn_card_ids.add(card.id)
            await self.broadcast({"type": "card_drawn", "card": card})
            return card
```

## ホスティング/コスト方針
コストを最小化するため、**Google Cloud Run(min-instance=0)**でのFastAPIデプロイを軸にする。リクエストがない間は課金されず、個人開発の利用規模なら無料枠内に収まる見込み。ただしWebSocketは接続時間に応じた課金となる点に注意し、長時間接続が常態化しないかは運用しながら確認する。代替案としてRenderの無料プラン(15分でスリープ、体験は劣るが完全無料)も選択肢に残す。フロントエンド(Next.js)はVercel、DB/AuthはSupabase、いずれも無料枠で運用する。

## 将来の拡張余地(任意)
将来的にリアルタイム共有部分などで並行処理・パフォーマンス上の必要性が明確になった場合は、その部分だけをGoのマイクロサービスとして切り出すことも可能。フロントエンドから見えるAPI/WebSocketの契約(エンドポイント仕様・メッセージフォーマット)さえ維持すれば、内部実装の移行は原理的に可能(コード自体は言語が異なるため再利用はできないが、FastAPIのOpenAPIスキーマや明文化したWebSocketメッセージ仕様がそのまま移行時の設計書になる)。ただし本アプリでその必要が生じる可能性は低く、あくまで保険的な選択肢と位置づける。
