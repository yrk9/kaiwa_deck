# テーブル設計

対話を通じて多対多の関係を洗い出し、中間テーブルで解消しながら設計した。

## ユーザ
- id: uuid
- ユーザ名: str
- メールアドレス(匿名ユーザーの場合はnull): str | null
- is_anonymous: bool(匿名ユーザーかどうか。ゲスト利用時も仮のユーザーレコードを作り、後からアカウント登録で昇格できるようにする)

## デッキ
- id: uuid
- 作成者id: uuid
- デッキ名: str
- 作った日: datetime
- 更新日: datetime

## deck_cards(デッキとお題の中間テーブル)
- deck_id: uuid
- card_id: uuid
- PRIMARY KEY: deck_id + card_id(重複登録は不可。並び順は管理しない)

## ルーム
- id: uuid
- ルームの作成者id: uuid
- deck_id(使用するデッキ。1ルームにつき1つだけ): uuid
- ルーム名: str
- 作った日: datetime

## room_users(ルームとユーザーの中間テーブル)
- room_id: uuid
- user_id: uuid
- joined_at(初回参加日時): datetime
- last_seen_at(最終アクセス日時。再入室のたびに更新): datetime
- PRIMARY KEY: room_id + user_id(重複登録は不可。再入室はUPDATEで対応)

## お題
- id: uuid
- 作成者id: uuid
- 内容(テキスト): string
- 補足(参加者に共有したい補足説明。お題自体に付随する固定の注記): string | null

## room_drawn_cards(ルームで引かれたお題の記録)
- room_id: uuid
- card_id: uuid
- drawn_at(引かれた日時): datetime
- PRIMARY KEY: room_id + card_id(同一ルームで同じお題は1回しか引けない)

## 備考
- 1人のユーザは複数のデッキを保存できる
- 1人のユーザは複数のルームに入れる
- 1つのデッキに複数のお題が入れる(deck_cards経由、同じお題は複数のデッキで使い回される)
- 1つのルームが使うデッキは1つだけ(ただし同じデッキを複数のルームで使うことはできる)
- ルーム単位で「いつ・どのお題が引かれたか」はDBに記録する(Cloud Runのmin-instance=0構成でインスタンスがスケールダウンしてもゲーム進行状態を復元できるようにするため)。ただし「誰が引いたか」は記録しない(room_drawn_cardsにdrawn_byは持たせない)

## 設計判断の経緯

- **デッキ⇔お題、ルーム⇔ユーザーの多対多**: 当初は配列(お題のリスト、ユーザーのリスト等)で持たせていたが、正規化・整合性・将来の集計機能を考慮し、それぞれ`deck_cards`・`room_users`の中間テーブルに分割した
- **ルーム⇔デッキ**: 当初は多対多(デッキのリスト)として考えていたが、「1ルームで同時に使うデッキは1つだけ」という要件を確認した結果、単純な1対多と判明し、`ルーム.deck_id`の外部キー1本に整理した
- **room_usersの重複制御**: 同じユーザーの再入室は新規行を増やさず、既存行(`last_seen_at`等)をUPDATEするUPSERT方式で対応する方針とした
- **ユーザーの匿名対応**: ゲスト利用(ログイン不要)を優先する方針([課題とペルソナ.md](./課題とペルソナ.md))に合わせ、匿名ユーザーも仮のユーザーレコードを持たせる設計(`is_anonymous`)とした。これにより、ゲスト利用中の履歴やお気に入りを後からアカウント登録で引き継げる
- **id型はUUIDに統一**: Supabase Auth採用によりユーザーIDが仕様上UUID固定になること、ルームやデッキのように外部共有されうるIDを連番にすると推測アクセス(IDOR)のリスクがあることから、全テーブルのidをUUIDに統一した
- **日時系カラムはdatetime**: `last_seen_at`のように同日中に何度も更新されうる値をdate型(年月日のみ)で持つと粒度不足になるため、時刻まで含むdatetime型に統一した
- **room_drawn_cardsの追加**: 当初「引いた記録は不要、フロントで管理する」としていたが、Cloud Run(min-instance=0)構成ではインスタンスがスケールダウンしうるため、ゲーム進行状態をDBに永続化する方針に転換した([API設計.md](./API設計.md)の「ルームの進行」節)。ただし「誰が引いたか(drawn_by)」は持たせない判断とし、これに伴い`/history`(個人がルームをまたいで引いた履歴)はPhase 2に送った
