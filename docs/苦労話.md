# 苦労話

環境構築・Supabase接続で実際に詰まった箇所と、その原因・解決策の記録。同じ罠に将来また引っかからないためのメモ。

## 1. Git Bashで`\\wsl.localhost\...`にmkdirできない

**症状**: `mkdir -p "//wsl.localhost/ubuntu/..."` が `Read-only file system` で失敗する。一方`cp`や`ls`は成功する。

**原因**: 不明(Git BashのMSYSレイヤーがこのUNCパスへのディレクトリ作成だけ弾いている様子)。`dangerouslySkipSandbox`を付けても再現。

**解決策**: ディレクトリ作成だけPowerShellの`New-Item -ItemType Directory`に切り替える。ファイルの読み書き(Write/Editツール、`cp`)は問題なく動く。

## 2. `docker run -v /app ...`がGit Bashのパス変換で壊れる

**症状**: `docker run --rm -v "$(pwd)/frontend:/app" -w /app node:20-slim ...` を実行すると `the working directory 'C:/Program Files/Git/app' is invalid` というエラーになる。

**原因**: Git Bash(MSYS2)は`/app`のようなUnix風パスを自動でWindowsパスに変換してしまう。DockerコンテナへのUnixパス指定(`-w /app`など)まで巻き込まれて壊れる。

**解決策**: `wsl.exe -d Ubuntu -- bash -c "..."` でWSLディストリ内から直接`docker`コマンドを実行する。WSL内はネイティブのLinuxパスなので変換の問題が起きない。

## 3. Docker Desktop再起動でWSL統合が切れる

**症状**: 前回まで動いていた`wsl.exe -d Ubuntu -- docker ...`が、ある時点から`The command 'docker' could not be found in this WSL 2 distro`で失敗するようになった。

**原因**: Docker DesktopのWSL統合(Settings → Resources → WSL Integration)が何らかの理由で無効化/切断された。

**解決策**: Windows側の`docker`コマンド(Docker Desktopのコンテキスト)からは引き続きdaemonに繋がっていたため、そちらを使う。`docker compose`自体はcompose fileの相対パスで解決するので、`-v /app`のような明示的なUnixパス指定さえ避ければWindows側からの実行でも問題ない。

## 4. `create-next-app`が既存ファイルを理由に失敗する

**症状**: `frontend/`ディレクトリに`Dockerfile`等を先に作っていたため、`npx create-next-app@latest .`が「contains files that could conflict」で止まる。

**解決策**: 一時的にDockerfile・.dockerignore・.env.local系のファイルを`/tmp`に退避 → 空になったディレクトリでscaffold実行 → 退避したファイルを戻す。

## 5. コンテナ内で生成したファイルがroot所有になる

**症状**: `docker run`(rootユーザーで実行されるコンテナ)経由で`create-next-app`や`npm install`を実行すると、ホスト側に生成されたファイルが全部root所有になり、WSL側の一般ユーザーから編集・削除しづらくなる。

**解決策**: `sudo`にパスワードが必要で使えなかったため、`docker run --rm -v <path>:/app alpine chown -R 1000:1000 /app`のように、rootで動く使い捨てコンテナ経由で所有者をホスト側のuid(1000)に戻す。

## 6. Supabaseの接続文字列: Direct connectionはIPv6専用

**症状**: `db.<project-ref>.supabase.co`(Direct connection)にbackendコンテナから接続すると`Network is unreachable`。

**原因**: SupabaseのDirect connectionエンドポイントはデフォルトでIPv6専用(IPv4接続には有料アドオンが必要)。DockerコンテナやネットワークがIPv6非対応だと繋がらない。

**解決策**: **Shared pooler**(`aws-0-<region>.pooler.supabase.com`、ユーザー名も`postgres.<project-ref>`形式に変わる)を使う。これはIPv4対応で追加コスト不要。「Dedicated pooler」もIPv6専用なので選ばないよう注意(紛らわしい)。

## 7. パスワードのプレースホルダー角括弧をそのまま貼ってしまう

**症状**: SupabaseのUIが`postgresql://postgres:[YOUR-PASSWORD]@...`のように表示するのを、`[実際のパスワード]`と角括弧ごと貼ってしまい接続失敗。

**解決策**: 角括弧は「ここを置き換えてください」という記法であり、実際のパスワードだけに置き換えて角括弧自体は消す。

## 8. `NEXT_PUBLIC_SUPABASE_URL`に余計なパスを付けてしまう

**症状**: `https://<project-ref>.supabase.co/rest/v1/`のようにパス付きで設定してしまう。

**原因**: Supabaseクライアントライブラリは渡されたURLに対して内部で`/auth/v1/`や`/rest/v1/`を自動的に付け足す設計。すでにパスが付いていると二重になりリクエストが壊れる。

**解決策**: `NEXT_PUBLIC_SUPABASE_URL`はベースURL(`https://<project-ref>.supabase.co`)のみにする。

## 9. `@supabase/supabase-js`がNode.js 20でクラッシュする

**症状**: `createClient()`を呼んだ瞬間に`Error: Node.js 20 detected without native WebSocket support`で例外。

**原因**: supabase-jsは内部でRealtimeClientを初期化する際にネイティブの`WebSocket`グローバルを要求するが、Node.js 20にはまだ標準搭載されていない(Node 22以降で安定サポート)。今回はSupabase Realtimeを使わずFastAPI自前のWebSocketを使う設計(`技術選定.md`)なのに、Authクライアントを作るだけでこの初期化が走ってしまう。

**解決策**: `frontend/Dockerfile`のベースイメージを`node:20-slim`から`node:22-slim`に変更。

## 10. Supabaseダッシュボードの「Anonymous Sign-Ins」トグルが保存されていなかった

**症状**: トグルをONにしたはずが、`signInAnonymously()`が`Anonymous sign-ins are disabled`エラーを返す。

**原因**: ダッシュボード側の保存操作(Saveボタン等)を経ずに離脱していた。

**解決策**: 設定画面に戻り、保存操作を確実に行ってから再試行。UIの保存ボタンの有無・トースト通知などを確認する習慣が必要。
