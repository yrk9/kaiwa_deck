# 苦労話

環境構築で実際に詰まったことのメモ。同じ罠に二度はまらないための記録。

## 1. Windows + WSL + Docker のパス問題

- **Git BashでDockerのパス指定が壊れる**: `-w /app` が `C:/Program Files/Git/app` に勝手に変換される(Git Bashの自動パス変換)。→ `wsl.exe -d Ubuntu -- bash -c "..."` でWSL内から実行して回避
- **Docker Desktopの再起動でWSL側から`docker`が使えなくなる**: WSL統合が切れた。→ Windows側の`docker compose`をそのまま使う
- **`\\wsl.localhost\...`で`mkdir`だけ失敗する**(原因は不明): → ディレクトリ作成だけPowerShellの`New-Item`かWSL経由で行う

## 2. コンテナで作ったファイルがroot所有になる

- **症状**: `docker run`で`create-next-app`や`npm install`を実行すると、生成ファイルがroot所有になり、普段のユーザーで編集・削除しにくい
- **対処**: `docker run --rm -v <path>:/app alpine chown -R 1000:1000 /app`で所有者を戻す(`sudo`にパスワードが要るため)

## 3. `create-next-app`が既存ファイルがあると止まる

- **対処**: Dockerfile等を一時的に退避 → 空のフォルダで実行 → 元に戻す

## 4. Supabaseへ接続できない(IPv6)

- **症状**: `Network is unreachable`
- **原因**: Direct connection(`db.xxx.supabase.co`)はIPv6専用で、Dockerコンテナから届かない。「Dedicated pooler」もIPv6専用
- **対処**: **Shared pooler**の接続文字列を使う(IPv4対応、追加料金なし)

## 5. Supabaseの設定値の書き方ミス

- **パスワードの`[ ]`**: `[YOUR-PASSWORD]`は「ここを置き換える」という意味の記法。`[ ]`ごと実際のパスワードに置き換える
- **`NEXT_PUBLIC_SUPABASE_URL`に`/rest/v1/`を付けた**: クライアントが内部で`/auth/v1/`などを付け足すので、`https://xxx.supabase.co`だけにする
- **匿名サインインのトグルが保存されていなかった**: ONにした後、保存できているか確認する

## 6. `@supabase/supabase-js`がNode 20でクラッシュする

- **症状**: `createClient()`で`Node.js 20 detected without native WebSocket support`
- **原因**: Node 20には標準の`WebSocket`が無い(Node 22以降にはある)。Realtimeを使わなくても、初期化時に必要になる
- **対処**: frontendのベースイメージを`node:22-slim`にする

## 7. JWTの検証方法が古い記事と違った

- **症状**: ダッシュボードの`JWT Secret`で検証すると`alg value is not allowed`
- **原因**: このプロジェクトのトークンは**ES256**(公開鍵方式)で署名されていた。`JWT Secret`はHS256時代のもので、記事の多くもHS256前提
- **対処**: 公開鍵の一覧(JWKS)を取得して検証する。実装前に、実際のトークンのヘッダで`alg`を確認するのが確実
